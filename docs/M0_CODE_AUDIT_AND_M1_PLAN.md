# M0 Code Audit and M1 Plan

**Audit basis:** `rovsen-tech/student-helper-pro`, branch `architecture/universal-learning-os`, HEAD `ce3798a4777114b8b95d7108a32e4b76472350be`. Clean before audit; architecture reference present. Findings below distinguish code inspection from executed tests. This audit does not certify production behavior.

## 1. Current architecture and behavior

- **Frontend:** React 19 + Vite 8, JavaScript/JSX, `frontend/src/App.js`; frontend API base is build-time `REACT_APP_BACKEND_URL` (`frontend/vite.config.mjs:76-86`, `frontend/README.md:8-11`). Views cover subject/textbook selection, tutor, uploaded books, notes, quiz, progress and parent dashboard.
- **Backend:** FastAPI app in `backend/server.py`, `/api` router (`:87`), Motor/MongoDB (`:34-36`), Emergent LLM integration configured as Gemini (`:38-40`, `:298-300`), Emergent object storage (`:42-80`), TTS integration/cache (`:593-626`). No login/account identity is implemented; `X-Student-Id` selects a profile (`:171-185`; `frontend/src/lib/studentSession.js:1-37`).
- **Collections/contracts observed:** `books`, `textbooks`, `sections`, `lessons`, `answer_keys`, `messages`, `students`, `student_profile`, `progress`, `quizzes`, `quiz_answers`, `activity_log`, `lesson_summaries`, `parent_settings`, `tts_cache`. Legacy textbook fields include stable `id`, `textbook_id`, `section_id`, order/title, page range, content blocks and `provenance`; chat history uses `session_id`, role/content/time and additive `archived` flag. These are compatibility contracts, not a complete formal schema.
- **Student/session:** selected profile persists in browser local storage and is sent as a header; invalid non-default IDs are checked against `students` (`server.py:179-185`). Chats key by book or subject/topic and student (`:160-168`); recent messages are loaded and streams are saved (`:443-449`, `:541-556`). Tutor stage/resume state is client-side (`TutorChat.jsx:245-272`).
- **Tutor:** lesson IDs select SOURCE blocks and page range (`server.py:429-439`); system prompt includes at most 3,500 source characters (`:259-263`), book explanation at most 4,000 (`:264-271`), and recent conversation context uses eight of the newest 20 messages (`:441-445`, `:510-514`). Diagnostic, recall, quiz and answer stages are prompt branches (`:454-508`). The frontend streams SSE and can resume a stage; no interrupt/cancel control was found. Failed/empty model streams return an error event and do not save an assistant message (`:524-545`), but the user message may already have been saved.
- **PDF and content:** uploaded PDFs are stored as objects and analyzed by Gemini into a summary/explanation; upload checks only the filename suffix (`server.py:355-413`). The textbook importer extracts text spans and remaps selected font text (`ingest_textbook.py:115-158`), guesses printed/PDF offsets from title anchors (`:161-174`), splits on heading strings (`:176-192`) and stores source text with page references. It does not extract page images, bounding boxes, layout, formula structure, or OCR; importer text is capped at 6,000 normalized and 8,000 original characters per block (`:260-270`). Tutor retrieval then truncates that source to 3,500 characters. `backend/mathbook.pdf` exists, but extraction quality/page fidelity was not run because PyMuPDF is unavailable in this audit environment.
- **Existing features:** quiz generation and validation, deterministic checks for some numeric answers, LLM fallback evaluation, answer ownership, XP/mastery/progress and duplicate-answer protection are implemented (`server.py:801-903`, `quiz_engine.py:162-281`, `progress_manager.py:59-90`, `:146-223`). Smart Notes are generated from submitted conversation text with bounded message/content counts (`server.py:629-655`, `smart_notes.py:104-153`); generation is client-fed and not persisted by that endpoint. Parent PIN has salted SHA-256 and throttling (`server.py:1040-1136`); parent dashboard reads stats, review, skill gaps, errors and summaries (`ParentPanel.jsx:40-64`). Review questions are derived from quiz mistakes/curriculum (`server.py:974-1012`). Browser TTS fallback and backend TTS are implemented (`useTTS.js:18-60`, `server.py:593-626`). No whiteboard/canvas/board-action renderer was found. Presence alone does not establish all runtime flows.

## 4. Minimal M1 implementation scope and sequence

M1 should be a compatibility foundation, not a tutor, ingestion, or frontend rewrite.

1. **Define versioned optional contracts** in a new `backend/learning_contracts.py`: program/source/content/objective/evidence/mastery metadata with schema version, validation and stable IDs. Do not make legacy fields required.
2. **Add read/serialization adapters** in `backend/server.py` (or a new `backend/learning_adapters.py`) that map existing `Textbook`/`Lesson` documents to source/content views while preserving current endpoint models and Mongo documents. Add no database backfill in M1.
3. **Add contract fixtures/tests** in new `backend/tests/test_learning_contracts.py` and `backend/tests/test_learning_adapters.py` for legacy documents, unknown optional fields, stable IDs and source/page round trips. Include explicit no-write/no-delete assertions for adapters.
4. **Document source versioning and safe importer invocation** in `docs/M1_DATA_CONTRACTS.md`; importer replacement/deletion logic must remain out of the M1 path. Any later importer change requires a separate dry-run/diff and backup/restore plan.

Sequence: contracts → adapter/unit tests using representative fixtures → review API compatibility/diff → user review before any later data migration. Defer objective-driven retrieval, new renderers, mastery algorithms, upload ingestion, AI orchestration and deployment changes to later milestones.
