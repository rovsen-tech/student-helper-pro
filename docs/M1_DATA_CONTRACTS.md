# M1 Learning Data Contracts

## Scope and persistence boundary

`backend/learning_contracts.py` defines version 1 Pydantic v2 data shapes, and `backend/learning_adapters.py` provides pure views over current textbook dictionaries. These contracts are not wired into existing API routes, MongoDB writes, ingestion, grading, rendering, or deployment. Current React, FastAPI, MongoDB and Emergent behavior is unchanged. The code does not read environment variables, make network calls, import `server.py`/`ingest_textbook.py`, generate identifiers, or persist data.

Each independently stored entity requires an explicit `schema_version: 1`. IDs are required for identity-bearing entities, validated as nonempty and without surrounding whitespace, and never generated by validation or adaptation. Unknown schema versions fail validation until explicitly supported. JSON output should use Pydantic's `model_dump(mode="json")`; timestamps/dates serialize as ISO strings, and absent optional contract data remains `null` or an empty collection according to the field definition.

## Contract purposes

| Contract | Purpose |
|---|---|
| `LearningProgram` | Describes a school, CEFR/IELTS, exam, university, law or professional program without assuming one grade system. |
| `SourceDocument` | Identifies an original source independently from its optional edition, effective date and revision; hash, URI, original asset and ingestion state are explicit. |
| `ContentNode` | Represents an ordered source hierarchy node with parent/document IDs, page references, structured blocks, optional extraction confidence and review status. |
| `LearningObjective` | Stores a program competency, prerequisites and optional explicit mastery criteria. It does not infer curriculum mappings. |
| `LessonPlan` | Orders objective and source-node references, explanation steps, practice blueprint and citations. |
| `BoardAction` | Carries inert, typed data for one of five allowlisted future actions; this package does not render or execute it. |
| `AssessmentItem` | Holds public prompt/response shape and references separately from private answer key, rationale, rubric and evaluator metadata. |
| `StudentEvidence` | Records an optional response, outcome, misconception tags and timestamp without grading it. |
| `StudentMastery` | Holds optional estimate/confidence and algorithm/review metadata; unknown estimates remain `null`. |
| `ExamBlueprint` | Defines optional objective/difficulty distributions, item count, duration and access policy. |

Nested types (`PageReference`, `SourceReference`, `MasteryCriteria`, `LessonStep`, `PracticeBlueprint`, and action payloads) exist to clarify shared fields; they do not introduce separate persistence requirements.

## Source fidelity, provenance and unknowns

Provenance is one of `SOURCE`, `DERIVED` or `GENERATED`; it is not guessed by the contracts. Content nodes distinguish unknown confidence/review status from verified values. No page reference, bounding box, curriculum mapping, edition, effective date, extraction confidence or mastery estimate is fabricated.

`PageReference.printed_page` and `PageReference.pdf_page` are separate positive integers and may independently be unknown. Bounding boxes require an explicit PDF page and coordinate system (`normalized` or `pdf_points`). Legacy `page_start`, `page_end` and `source_page` are not mapped to either verified page field because their semantics are ambiguous in the current importer. The adapter retains them unchanged under `legacy_metadata` and `legacy_record`.

The current importer emits textbook `id/subject_id/title/grade/edition/grif/provenance/created_at`, section `id/textbook_id/order/title`, lesson `id/textbook_id/section_id/order/number/title/page_start/page_end/content`, and content blocks with `type/provenance/text/normalized_text/original_text/page_start/page_end/source_page`. These are preserved as the adapter's source snapshot. The typed view maps only known, defensible relationships: textbook ID/title and an explicitly supplied edition to `SourceDocument`; section ID/textbook ID/title/order to a `ContentNode`; lesson ID/textbook ID/section ID/title/order and content blocks to a `ContentNode`; block type/provenance/text variants to `ContentBlock`.

## Legacy metadata and reconstruction

Each adapter result has three disjoint areas: a typed `contract`, clearly labeled `legacy_metadata` for fields not represented as verified contract facts, and `legacy_record` containing a deep-copied source document. This separation avoids collisions between legacy keys and contract keys. Unknown top-level lesson fields and unknown per-content fields are retained; page fields remain legacy metadata. Missing, explicit `null`, and empty lists/maps remain distinct in the snapshot.

`reconstruct_legacy_document` returns a deep copy of that exact source shape. Exact reconstruction is guaranteed only for supported JSON-compatible mappings: `null`, strings, booleans, finite numbers, lists and dictionaries with string keys. Arbitrary MongoDB BSON values, custom Python objects, tuples, non-finite numbers, or dictionaries with non-string keys are rejected rather than claimed as losslessly serializable. Reconstruction uses the retained source record; it does not reverse-engineer data from the typed view.

Legacy required IDs, titles/types, relationships, content strings, provenance, order and page ranges are validated. Invalid values raise an error; adapters do not silently repair them. Existing legacy model defaults are reflected only where those models specify them (for example, omitted `order` defaults to zero and omitted block provenance defaults to `SOURCE`); the original snapshot still records that the key was absent.

## Assessment privacy

Answer keys, distractor rationale, rubrics, evaluator metadata and nested private metadata live under `AssessmentItem.private`. `student_facing_projection()` manually constructs an allowlist containing only schema version, item ID, objective IDs, difficulty, prompt, response type, options and source references. It does not call a generic full-model dump, and private values do not appear even when nested. No grading or authorization behavior is implemented here; callers must continue to enforce access control when contracts are eventually integrated.

## Board actions

The closed vocabulary is `write_text`, `write_math`, `draw_shape`, `highlight` and `clear`. Each action has a discriminated payload with only typed data fields; unknown fields (including `script`/handler-style fields), unsupported kinds, mismatched action/payload kinds, invalid geometry and invalid points fail validation. Text and math expressions are inert strings. No expression evaluation, HTML rendering, scripting, or action execution is provided. Extensions require a reviewed schema and renderer allowlist change, not arbitrary payload keys.

## Migration, rollback and deployment

These models and adapters do not migrate or change current API/database shapes. Any future integration must first add compatibility tests against real legacy fixtures, preserve existing IDs and response contracts, use additive/versioned records, and perform a separately reviewed read-only inventory and backup/restore exercise before any migration. Rollback should disable/revert the adapter integration while leaving legacy records untouched. Importer execution or database migration requires separate explicit approval; this M1 work does neither.

No Emergent deployment change is included. A future deployment must separately confirm backend launch/port/proxy/health behavior, build-time `REACT_APP_BACKEND_URL`, server-only Mongo/LLM/storage secrets, CORS origins, and pinned dependency availability. These contracts introduce no new dependencies or environment settings.
